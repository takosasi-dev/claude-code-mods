# mod の重さ

`node tools/perf.mts` で測り直せます(全部で 10 分ほど。`--runs=N` で回数、mod の名前を渡すとその mod だけ)。
下の印の間は perf.mts が書き直します。印の外は手で書いた物です。

## 測り方

- **起動から終わりまで**: headless の `claude -p "<プロンプト>"` を node から走らせ、プロセスが終わるまでの時間。
  - 読み込み: 組み込みの `/color`(その場で終わり、モデルを呼ばない)を渡す。mod を 1 本だけ `--plugin-dir` で読ませた時と、何も読ませない時の差が、その mod を読み込む重さ(`session.start` を含む)。
  - コマンド: その mod のコマンド(`hooks/register.tsx` で登録する名前のうち、組み込みと被らない 1 つ目)を渡す。ペインを開く処理まで入る。
  - 機械の揺れが偏らないよう、mod なし・読み込み・コマンドを 1 回ずつ交互に走らせ、それぞれの中央値を取る。
- **依頼者の設定を効かせない**: `~/.claude/settings.json` の env に `CLAUDE_CODE_PLUGIN_DIRS`(全 mod)が入っていて、何もしないと毎回全部読まれる。次の 3 つで切った。
  1. 子の env から `CLAUDE_CODE_PLUGIN_DIRS` を消す(Claude Code の中から走らせると、親から受け継いでいる)
  2. `CLAUDE_CONFIG_DIR` を一時フォルダにする(settings.json も mod の store もそちらに行き、本物の `~/.claude/plugins/store` に書かない)
  3. `--setting-sources project` と、空の一時フォルダを作業フォルダにする
  - 効いていないことは、毎回 stream-json の init の `plugins` 一覧が読ませた mod だけ(組み込みの 2 本を除く)かで確かめ、違えば止まる。env に残すと `--setting-sources project` でも全 mod が読まれ、`CLAUDE_CONFIG_DIR` を替えないと store が本物に書かれることを確かめた。
- **モデルを呼ばない**: `ANTHROPIC_BASE_URL` を閉じた口(`http://127.0.0.1:9`)に向けておく。結果が `num_turns` 0・`duration_api_ms` 0・`api_retry` が無い・返事が全部 `<synthetic>` の時だけ採り、外れたらその場で止めて表に「モデル」と出す。知らないスラッシュコマンドは文としてモデルへ送られる(試した時は `api_retry` が出て、閉じた口なので届かなかった)。
- **SVG**: `tools/shots.mts` の SHOTS の関数(架空のデータを作る所も含む)を node で呼んだ時間。初回は mod のモジュールを読む時間を含む。2 回目以降は 5 回の中央値。字数は Svg の source の上限(131,072 字)と比べる用。
- 1 回ずつの値は 620 ms 前後と 780 ms 前後の 2 か所に分かれやすく、mod ごとの差は ±100 ms ほど揺れる。下の「見当」では、何度測っても目立つ物だけを挙げた。

## 見当と直す案

port-watch と wait-games は 0.7.0 で直した(下の各項)。ほかは案のまま。

- **mod を 1 本読むと、どれでも 150 ms ほど遅くなる。** 中身の小さい work-bar・danger-frame・reply-frame でも +100 ms 前後になる時が多く、大半はエンジンが mod の仕組み(フックを動かす所)を立ち上げる分と見ている。全部(41 本)読ませると +1.4〜1.5 秒で、2 本目からは 1 本あたり 30 ms 台。mod 側で減らせるのは 1 本あたりの数十 ms の方。
- **port-watch の `/ports` (+770 ms)**: いちばん重い。`openPane` が `refresh` を await していて、`netstat -ano` と `tasklist` が終わるまでコマンドが返らない。
  - 案: ペインを先に開いて「読んでいます」を出し、`void refresh($)` で裏で読む(`session.start` の 1 秒後の読みと同じ形)。
  - **0.7.0 で直した**(port-watch 0.2.1)。直した直後の測定で +794 → +230 ms。上の表の値は、ほかの作業で機械が混んでいた時の測り直し。
- **canvas-pane の読み込み (+250 ms、毎回)**: ほかの mod より 100 ms ほど重い。`session.start` で `$.tool.register` を呼ぶのはこの mod だけで、ツールを登録するとエンジンがツールの口(MCP の形)を作る分と見ている。
  - 案: ツールはモデルに見せるために始めから要るので、減らすのは難しい。気になるなら設定で「ツールを出さない」を選べるようにする。
- **dev-rpg の読み込み (+240 ms、毎回) と SVG の初回 (29 ms)**: hooks の TS がいちばん大きい(rpg.ts 47KB・battle.ts 31KB)。読み込みのたびに型を外して読む分と、`session.start` での store の読み書きが多い分と見ている。SVG は 2 回目以降 1 ms 未満なので、初回の 29 ms はほぼモジュールの読み込み。
  - 案: 実績の書・戦いなど、開いた時だけ要る画面の処理を別のファイルに分け、`session.start` では読まない形にできるかを試す(エンジンがフックの中の動的 import を許すかは未確認)。
- **wait-games**: 読み込み +210 ms、SHOTS の関数が 2 回目以降も 30〜50 ms。SVG を作る所(`sudokuSvg` は 1 ms 未満)ではなく、9x9 の数独を作る `newSudoku` が重い(単体で 55〜80 ms)。マスを 1 つ消すたびに `countSolutions` を呼び、その中で毎回 81 マスの `peers` を作り直し、マスごとに Set と配列を作っている。モジュールを読んだ時にも `newSudoku(4, …)` を 1 回呼ぶ(4x4 なので軽い)。
  - 案: `peers` の表をマスの数ごとに 1 回だけ作って持つ、候補を Set ではなくビットで持つ。「新しい盤」のボタンを押した時の待ちが短くなる。
  - **0.7.0 で直した**(wait-games 0.2.1)。`newSudoku(9)` は約 58 ms → 約 2 ms、出る盤は同じ。表の SVG の欄の初回の値はモジュールを読む分。
- **SVG の大きさ**: いちばん大きいのは dev-rpg(30.6K 字)・aqua-pet(29.7K 字)で、上限 131,072 字の 4 分の 1 以下。描き直しの多い work-bar・face-band は 2.5K〜4K 字と小さい。今は心配ない。
